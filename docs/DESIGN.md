# 최종 프로젝트 설계안

**Evidence-Grounded Forensic Reconstruction and Investigation Target Discovery**

이기종 AI 코딩 에이전트의 포렌식 행위 복원 및 증거 기반 조사 대상 후보 발굴

| 항목 | 내용 |
|------|------|
| 문서 버전 | 1.1 |
| 작성일 | 2026-10-19 |
| 상태 | 구조 확정 · 세부 규칙 진행 중 (§7.4~7.5, 부록 A 참조) |

## 1. 프로젝트 개요

### 1.1 핵심 목표

서로 다른 AI 코딩 에이전트의 아티팩트를 공통 형식으로 통합하고, 기록된 행위와 독립적으로 관측된 실행 증거를 연결해 행위 관계를 복원한다. 이어 프로비넌스 그래프를 활용해 문자열·IOC 검색만으로는 놓칠 수 있는 조사 대상 후보를 찾고, 각 후보의 근거와 불확실성을 제시한다.

이 프로젝트는 **새로운 범용 AI 포렌식 플랫폼을 처음부터 만드는 것이 아니다.**  
기존에 개발 중인 네 종류의 파서와 공통 모듈을 활용하고, 그 위에 **관계 기반 조사 대상 발굴**과 **정량적 성능 검증**을 핵심 기능으로 추가한다.

### 1.2 연구 질문

> 동일한 AI 코딩 에이전트 증거에서 프로비넌스 그래프와 증거 교차검증을 활용하면, 문자열·IOC 기반 추출 또는 정규화 이벤트 단독 검색보다 증거로 뒷받침되는 조사 대상 후보와 행위 관계를 더 정확하게 복원할 수 있는가?

여기서 ‘새로운 대상’은 현실 세계에서 최초로 발견된 피해자를 뜻하지 않는다.  
사전에 제공한 IOC 목록에 의존하지 않고, **통제된 실험 데이터에서 정답으로 지정된 대상을 증거 관계를 통해 복원하는 것**을 의미한다.

### 1.3 최종 발표 정의

> 본 시스템은 이기종 AI 코딩 에이전트의 아티팩트와 독립적인 실행 관측 자료를 통합해 행위 간 증거 관계를 복원하고, 관계 기반 분석이 단순 검색보다 조사 대상 후보를 얼마나 정확하게 발굴하는지 평가한다.

## 2. 전체 시스템 구조

```
1. 증거 확보
   ├── 통제된 에이전트 시나리오
   ├── 하네스 · OS · 테스트 서버 관측
   └── 독립 정답 데이터
2. 이기종 아티팩트 파싱
   ├── Cursor Parser
   ├── Codex Parser
   ├── Claude Code Parser
   └── Antigravity Parser
3. 공통 정규화 및 추출
   ├── Canonical Event (행위 유형 · 태그 · 시각 정규화)
   └── 대상 엔터티 추출 (도메인 · IP · URL · 호스트)
4. 증거 대조 및 그래프
   ├── 명시적 ID · 참조 연결
   ├── 명령 · 시간 · 경로 · 프로세스 대조
   ├── 엔터티 해소 및 별칭 관계
   └── 프로비넌스 그래프 (노드 · 엣지 · 근거 · 충돌)
5. 통합 저장 및 검색
   ├── 원본 증거 저장소
   ├── 정규화 이벤트 · 엔터티 DB
   ├── 엣지 · 증거 · 규칙 DB
   ├── 정확 검색 · 전문 검색
   └── 선택적 벡터 검색
6. 조사 대상 분석
   ├── 조사관 질의 또는 자동 후보 발굴
   ├── 관련 이벤트 검색
   ├── 부분 그래프 탐색
   ├── 관계 근거 · 모순 · 관측 범위
   └── 대상 후보 우선순위화 → 행위 검증 카드 · 대상 카드 · 리포트
7. 별도 실험 및 평가
   ├── 4개 비교 실험
   ├── 평가 결과로 규칙 개선
   └── 성능 보고
```

### 운영 과정 vs 실험 과정

| 구분 | 설명 |
|------|------|
| **실제 조사 과정** | 확보된 증거를 파싱하고, 기존 DB와 그래프를 검색해 분석 결과를 생성한다. |
| **실험 과정** | 통제된 환경에서 실제 수행 결과를 독립적으로 수집해 관계 생성 규칙과 후보 발굴 성능을 검증한다. |

실제 조사 중에 과거 행위를 재실행하는 것이 아니다.  
재실행은 규칙을 개발하고 평가하기 위한 **별도의 검증 절차**이다.

## 3. 단계별 기능과 처리 흐름

### 3.1 1단계. 증거 확보 및 아티팩트 탐색

목적은 증거를 보존하고, 추출된 정보가 어디에서 나왔는지 추적 가능하도록 만드는 것이다.

| 기능 | 처리 내용 |
|------|----------|
| 입력 | E01·RAW·DD 이미지 또는 확보된 디렉터리 |
| 무결성 | 이미지·파일 해시 및 수집 정보를 기록 |
| 아티팩트 탐색 | 에이전트 기록과 관련 OS 아티팩트를 식별 |
| 원본 참조 | 파일 경로, 레코드 위치, 아티팩트 식별자 보존 |
| 수집 상태 | 발견·미발견·미수집·미지원·파싱 실패를 구분 |

이 단계에서는 피해 여부나 행위의 인과관계를 판단하지 않는다. **원본과 출처를 관리하는 것이 핵심**이다.

### 3.2 2단계. 에이전트별 독립 파싱

4개의 파서는 유지하되 각각의 원본 구조를 이해하는 책임을 분리한다.

| 파서 | 고려할 아티팩트 |
|------|----------------|
| Cursor | SQLite 상태 DB, 대화 트랜스크립트, 체크포인트, 도구 및 관련 실행 기록 |
| Codex | 세션 JSONL, 도구 호출·결과, 명령 이력 등 |
| Claude Code | 세션 기록, 도구 호출·결과, 프로젝트 및 하위 에이전트 관련 기록 |
| Antigravity | 확보된 대화·에이전트 기록 및 명령 실행 관련 아티팩트 |

- 각 파일이나 이벤트가 모든 환경에서 존재한다고 가정하지 않는다.
- 각 파서는 원본 이벤트 유형, 원본 필드, 파싱 오류, 원본 참조를 보존한다.
- 공통 스키마에 매핑되지 않는 필드는 버리지 않고 `extensions` 또는 미해석 기록으로 남긴다.

**출력:** 원본과 연결된 에이전트별 파싱 결과.

### 3.3 3단계. 공통 정규화·분류·태깅

정규화 모듈은 파서별 이벤트를 검색과 관계 분석에 사용할 수 있는 공통 형태로 바꾼다.

#### 권장 공통 이벤트 필드

| 필드 | 의미 |
|------|------|
| `event_id` | 정규화 이벤트 ID |
| `source_agent` | 출처 에이전트 |
| `native_event_type` | 원본 이벤트 유형 |
| `event_type` | 공통 이벤트 유형 |
| `source_session_id` | 원본 세션 ID |
| `normalized_session_id` | 내부 공통 세션 ID |
| `actor` | user, agent, tool, system, unknown |
| `timestamp`, `time_source` | 시각과 그 출처 |
| `command`, `file_path` | 명령·경로 등 추출 정보 |
| `tags` | 파일 작업·네트워크·권한·삭제 등 분류 |
| `raw_payload_ref` | 원본 이벤트 참조 |
| `extensions` | 에이전트 고유 필드 |

#### 반드시 분리해야 하는 개념

| 개념 | 의미 |
|------|------|
| `command_request` | 명령 실행 요청이 기록됨 |
| `tool_result` | 도구 결과 기록이 존재함 |
| `command_execution_observed` | 별도 증거로 명령 실행이 관측됨 |
| `file_change_observed` | 파일 변경을 뒷받침하는 별도 관측 증거가 존재함 |

도구 호출에 Shell이나 run_command가 있다는 이유만으로 `command_execution_observed`로 바꾸면 안 된다.  
공통화는 이름만 통일하는 것이 아니라, **이벤트의 의미를 정확하게 구분하는 작업**이다.

### 3.4 4단계. 조사 대상 엔터티 추출과 해소

#### 핵심 실험 대상 (이번 범위)

- **도메인 · IP · URL · 호스트명**
  - 프롬프트, 명령 인자, 에이전트 출력, OS·네트워크 관측에서 추출
  - 동일한 대상의 여러 표현은 근거가 있을 때 연결

- **파일 경로**
  - 피해 대상 후보의 핵심 범위라기보다는 **행위 그래프의 자원 노드**로 사용
  - 명령과 파일 작업의 연결을 복원하는 데 필요

계정·조직·클라우드 리소스는 확장 가능한 구조로 남기되, **이번 핵심 성능 평가에서는 제외**한다.

#### 엔터티 해소 원칙

가장 위험한 것은 **잘못된 병합**이다.

- 서비스 이름, 호스트명, IP가 비슷한 시각에 등장했다고 해서 자동으로 동일한 대상이라고 확정하지 않는다.
- 정규화, DNS 응답, 명령 인자, 실제 네트워크 기록, 테스트 환경의 별칭 설정 등 **근거를 활용**해 관계를 연결한다.
- 근거가 부족하면 동일 엔터티로 합치지 않고 `POSSIBLE_ALIAS` 같은 **후보 관계**로 남긴다.

**출력:** 정규화된 엔터티와 엔터티 간 관계 후보.

### 3.5 5단계. 교차검증 및 프로비넌스 그래프

그래프는 대화와 명령을 시간순으로 늘어놓는 것이 아니라, **각 행위가 어떤 요청·도구·실행·파일·대상과 연결되는지**를 표현한다.

#### 노드 유형

세션, 메시지, 도구 호출, 프로세스, 파일, 도메인·IP 등의 대상

#### 엣지 필수 필드

| 필드 | 의미 |
|------|------|
| `source_id`, `target_id` | 연결 노드 |
| `relation_type` | 관계의 의미 |
| `supporting_evidence_ids` | 근거가 되는 이벤트·관측 ID |
| `evidence_status` | 해당 사례의 확인 상태 |
| `basis_type` | 명시적 기록 · 교차검증 · 추정 등 |
| `rule_id`, `rule_version` | 관계 생성 규칙 |
| `contradiction_ids` | 모순되는 증거 |
| `observation_scope` | 어떤 관측 자료와 범위가 확보됐는지 |

관계를 생성한 **규칙의 검증 성능**과, 실제 사건에서 해당 관계를 뒷받침하는 **증거의 수준**은 서로 다르다.

## 4. 행위·대상 상태 판정 기준 (L0–L4)

| 단계 | 상태 | 최소 근거 | 결론의 한계 |
|------|------|----------|------------|
| L0 | `MENTIONED` | 원본 기록에서 대상이 언급됨 | 대상과 실제 행위의 관련성은 미확인 |
| L1 | `REQUESTED_OR_CLAIMED` | 작업 요청 또는 수행 주장이 기록됨 | 실제 수행 여부는 미확인 |
| L2 | `ATTEMPT_RECORDED` | 도구 호출·명령 시도 기록이 존재함 | 실제 실행은 별도 확인 필요. 오류·차단·타임아웃도 기록 |
| L2.5 | `TOOL_OUTPUT_RESPONSE` | 연결된 도구 결과에 상태 코드·배너·응답 등의 정보가 있음 | 도구 출력에 나타난 응답이며, 독립적인 확인은 아님 |
| L3 | `INDEPENDENTLY_OBSERVED` | OS·네트워크 등 독립 관측 자료가 행위를 뒷받침함 | 대상 서버의 처리 결과까지 입증하지 않을 수 있음 |
| L4 | `TARGET_EFFECT_OBSERVED` | 대상 측 로그나 상태 자료로 요청·변경 등 결과가 관측됨 | 관측된 효과가 곧 피해 확정인 것은 아님 |

이 단계들은 엄밀한 단일 점수라기보다, 조사관이 증거 수준을 이해하기 위한 표현이다.

#### 내부적으로 독립 기록하는 항목

- 에이전트의 요청·주장·도구 호출 여부
- 도구 출력에 응답 증거가 존재하는지
- OS·네트워크에서 실제 행위가 관측됐는지
- 대상 측에서 결과가 관측됐는지
- 증거가 부족하거나 상충하는지

## 5. 엣지 유형별 확정 규칙

| 관계 유형 | 생성 조건 | 확정에 필요한 근거 | 그 근거만으로 말할 수 없는 것 |
|-----------|----------|-------------------|------------------------------|
| `BELONGS_TO` | 이벤트와 세션의 연결 | 원본 세션 ID 또는 검증된 참조 | 유사한 시간이라는 이유만으로 같은 세션이라고 할 수 없음 |
| `CALLS` | 메시지와 도구 호출의 연결 | 명시적인 호출 ID·참조 또는 검증된 구조 | 요청이 실제 실행되었다고 할 수 없음 |
| `REQUESTS_READ` | 파일 읽기 요청 | 원본 도구 요청 및 대상 경로 | 파일 내용이 실제로 읽혔다는 사실 |
| `TOOL_REPORTED_READ` | 도구 결과에 파일 내용이 반환됨 | 결과와 호출·경로의 연결 | OS 수준에서 어떤 프로세스가 어떤 방식으로 파일에 접근했는지 |
| `FILE_CHANGE_OBSERVED` | 파일 생성·수정이 독립적으로 관측됨 | 파일 상태 변화 또는 관련 OS 기록 | 시간적 인접성만으로 특정 명령이 그 변경의 원인이라고 단정할 수 없음 |
| `NETWORK_ACTIVITY_OBSERVED` | 프로세스·통신 대상과 네트워크 활동의 연결 | OS 네트워크 기록 또는 패킷 관측 | 서버가 요청을 처리했거나 데이터를 받았다는 사실 |
| `SERVER_REQUEST_OBSERVED` | 대상 서버가 요청을 기록함 | 서버 접근 로그 등 대상 측 관측 | 해당 요청이 공격이거나 피해를 유발했다는 사실 |
| `REQUESTS_TARGET` | 명령·요청에서 대상이 지정됨 | 원본 요청 또는 명령 인자 | 실제 접근·피해 여부 |
| `POSSIBLE_ALIAS` | 다른 표현이 동일한 대상일 가능성 | DNS, 설정, 별칭 매핑 등 보조 단서 | 동일한 엔터티라고 확정할 수 없음 |

**핵심 규칙:** `REQUESTS_*`와 `*_OBSERVED`를 분리한다.  
요청 관계는 원본 요청 기록으로 확정할 수 있지만, 실행이나 대상 측 결과 관계는 각 단계에 해당하는 증거가 있어야 확정할 수 있다.

## 6. DB와 검색 구조

2개월 안에 별도의 그래프 DB를 새로 도입하는 대신, **기존 DB를 활용해 시작**한다.

### 6.1 핵심 테이블

| 테이블 | 역할 |
|--------|------|
| `artifacts` | 원본 파일과 출처, 해시, 수집 범위 |
| `events` | 정규화 이벤트, 시각, 행위 유형, 원본 참조 |
| `entities` | 도메인·IP·URL·호스트명·파일 등 노드 |
| `event_entities` | 이벤트와 엔터티의 관계 |
| `edges` | 프로비넌스 그래프의 연결 관계 |
| `edge_evidence` | 엣지를 뒷받침하거나 반박하는 근거 |
| `observations` | OS·네트워크·테스트 서버에서 수집한 관측 자료 |
| `rules` | 관계 생성 규칙과 버전 |
| `parser_runs` | 파서 실행 상태, 오류, 처리 결과 |

엣지에는 `rule_id`, `evidence_status`, `contradiction_ids`를 필수 필드로 둔다.

### 6.2 검색 흐름

1. **정확 검색:** 세션 ID, 파일 경로, 명령어, IP, 도메인, URL
2. **전문 검색:** 프롬프트·응답·로그 내용의 키워드 검색
3. **벡터 검색 (선택):** 질문 표현이 기록과 다를 때 의미 기반 검색을 보완
4. **그래프 탐색:** 검색 결과를 시작점으로 관련 행위·대상·증거의 연결 경로를 탐색

파싱·정규화와 기본 관계 구성은 **사전에** 하고, 질의 시에는 관련 이벤트와 **부분 그래프**만 탐색한다.

## 7. 조사 대상 후보 발굴 엔진

이 모듈이 최종적으로 사용자에게 제공할 **핵심 기능**이다.

### 7.1 처리 흐름

```
대상 엔터티 추출
    → 표기 정규화
    → 후보 별칭 및 관련 엔터티 탐색
    → 대상과 관련 행위의 그래프 경로 확인
    → 근거 · 모순 · 관측 범위 검토
    → 후보별 조사 우선순위 계산
    → 대상별 증거 카드 출력
```

### 7.2 우선순위 계산 요소 (설명 가능한 규칙)

| 요소 | 설명 |
|------|------|
| 관계의 직접성 | 명시적인 식별자 연결인지, 간접 추론인지 |
| 증거 출처의 독립성 | 같은 로그의 반복인지, 별도 OS·네트워크 자료의 뒷받침인지 |
| 행위 수준 | 단순 언급인지, 시도·관측·대상 측 결과까지 있는지 |
| 모순 및 불확실성 | 반대 증거가 있는지, 관측 범위가 충분한지 |

등장 횟수가 많다고 우선순위를 높게 주지 않는다.  
같은 문자열이 프롬프트에서 여러 번 반복되는 것과 독립적인 증거가 여러 개 일치하는 것은 다르다.

### 7.3 결과 카드 예시 (가상)

```
조사 대상 후보
────────────────────────────────
대상: api-lab.test
발견 경로: 사용자 메시지 → 도구 호출 → 명령 요청 → 네트워크 관측

원본 언급              확인
명령 요청              확인
독립 네트워크 관측      확인
대상 측 요청 기록       미확인

해석: 관련 행위와 네트워크 활동이 관측되어 후속 조사 대상으로
      선정할 수 있다. 다만 대상 서버 측 결과와 피해 여부는
      추가 증거가 필요하다.

다음 조사 항목: 대상 서버의 접근 로그가 확보되어 있다면
                해당 시각과 요청을 비교한다.
```

### 7.4 구현 구조 (현재 코드 기준)

조사 엔진은 `src/investigation/` 패키지이며, 단계별 책임을 모듈로 나누고 모듈 사이의 입출력은 `models.py`의 자료형(`Entity`, `Mention`, `Observation`, `Edge`, `Graph`, `Assessment`, `Candidate`, `InvestigationResult`)으로만 주고받는다. 런타임에서는 일반 dict이므로 `investigation.json` 형식은 그대로다.

```
events ──► extraction ──► Entity + Mention ─┐
raw obs ─► observations ─► Observation ─────┼─► graph ─► Graph ─► scoring ─► Assessment ─► cards ─► Candidate
                           └─► extraction ──┘
                                   core.py: 단계 조율 + 기존 공개 API 유지
```

| 모듈 | 책임 | 판단 범위 |
|------|------|-----------|
| `models` | 공통 자료형·상수 | 없음 |
| `observations` | 독립 관측 정규화·로딩 | 관측 상태·출처·원본 참조 |
| `extraction` | 도메인·IP·URL·호스트 추출과 표기 정규화 | 무엇을 대상으로 볼 것인가 |
| `graph` | 노드와 엣지(MENTIONS, COMMAND_REQUESTS, OBSERVES, CORROBORATES, CONTRADICTS, RESOLVES_TO) | 어떤 관계를 근거와 함께 만들 것인가 |
| `scoring` | 증거 수준·점수·우선순위 (`Assessment`) | 증거가 얼마나 강한가 |
| `cards` | 설명 문구가 붙은 카드와 Markdown | 표현만, 판단 없음 |
| `core` | 단계 조율, `build_investigation_result` 등 기존 API | 없음 |

호출부(`pipeline`, `normalizer`)는 `from investigation import ...`만 사용하므로 내부 모듈이 바뀌어도 영향이 없다.
에이전트 아티팩트만으로는 증거 수준이 `lead`를 넘지 못한다는 불변식을 `scoring`이 지킨다.

### 7.5 미해결 규칙과 수정 위치

아래 항목은 구조는 정해졌으나 규칙은 미완성이다. 각각 `tests/test_investigation_open_rules.py`에 `xfail(strict=True)`로 원하는 동작이 고정되어 있다. 수정이 끝나면 xfail을 제거하고, 변경된 출력을 검토한 뒤 `tests/baseline/golden_output.json`을 재생성한다.

| 규칙 | 현재 문제 | 수정 위치 |
|------|-----------|-----------|
| `observation-contract` | `collection_status` 누락 시 `observed`로 처리, 출처 `unknown`·원본 참조 없음도 허용 | `observations.py` |
| `entity-level-correlation` | 관측이 이벤트 ID로만 연결되어 같은 이벤트의 다른 대상까지 상관관계가 전파됨 | `graph.py`(엔터티 단위 엣지) + `scoring.py` |
| `filename-false-positive` | `main.py`, `config.json` 같은 파일명이 도메인으로 추출됨 (`.test` 등 실험 도메인은 유지해야 하므로 TLD 목록만으로는 불충분) | `extraction.py` (URL·명령 인자·경로 문맥) |
| `score-weights` | 점수 가중치·우선순위 임계값은 임시값 | `scoring.py` (평가 정답 데이터 확보 후) |

변경 보호 장치: `tests/test_investigation_baseline.py`는 대표 입력의 전체 출력을 고정한 구조 변경 회귀 테스트다.

## 8. 독립 정답 데이터와 통제 실험

이 단계가 **연구 성립의 핵심**이다.  
시스템이 분석한 에이전트 로그만으로 정답을 만들면 순환 논리가 된다.

### 8.1 권장 실험 환경

| 구성 | 역할 |
|------|------|
| ① Windows 테스트 PC | Cursor·Codex 등에서 통제된 작업 수행. Sysmon(프로세스·네트워크·파일) + Procmon 보완 |
| ② 별도 Linux 테스트 서버 | 격리된 테스트용 HTTP 서버. 서버 접근 로그와 서버 측 상태 수집 |
| ③ 독립적인 테스트 하네스 | 계획한 행위와 실제 수행된 행위를 구별 기록. 실제 명령, 반환 코드, 파일 전후 해시, 테스트 대상, 시각, 기대 관계 |
| ④ 정답 데이터 분리 | 실제 수행·관측 결과와 기대 엣지·대상 목록을 평가용 정답으로 보관. **분석 시스템에는 정답 목록을 제공하지 않음** |

모든 관측 수단을 전부 구현할 필요는 없다.  
핵심 실험에서 다룰 관계에 필요한 **독립 채널만** 선택한다.

### 8.2 개발용 / 평가용 시나리오 분리

- 개발 중에 규칙을 고칠 때 사용한 시나리오로 최종 성능을 측정하면 결과가 과도하게 좋아질 수 있다.
- 개발용 데이터로 규칙을 수정하고, **최종 평가는 별칭 함정·동시 실행·실패·로그 누락 등 변형한 별도 시나리오**에서 수행한다.

## 9. 비교 실험 4개

프로젝트의 핵심 기여는 기능 목록이 아니라 **실험 결과로 입증**해야 한다.

### 실험 1. 조사 대상 후보 발굴 성능

> **공정성 원칙 (코드: `src/evaluation/experiments.py`).** 모든 방식은 동일한 `ExperimentInput`을 받는다. 독립 관측 자료를 C에만 주면 방식의 효과와 입력 추가 효과가 섞이므로 실험을 둘로 나눈다.
> - **실험 1a (동일 입력 비교):** A·B·C 모두 독립 관측 없이 같은 이벤트만 입력한다. 추출·해소·그래프 방식의 효과만 본다.
> - **실험 1b (독립 관측 효과):** 같은 엔진 C를 관측 없이/있게 비교한다. 추가 증거의 효과만 본다.

**연구 질문:** 그래프 기반 엔터티 해소가 단순 문자열·IOC 추출보다 정답 대상 후보를 더 잘 복원하는가?

| 비교군 | 방식 |
|--------|------|
| A | 문자열·정규식·IOC 기반 추출 |
| B | 정규화 이벤트의 대상 필드 검색 |
| C | 엔터티 해소와 프로비넌스 관계를 활용한 후보 발굴 |

**지표:** 엔터티 Precision · Recall · F1, Precision@5, 잘못된 엔터티 병합률, 잘못된 대상 연결 비율(`wrong_link_rate`), 증거 과승격 비율(`over_promotion_rate`)

**구현 상태:** 방식 A/B/C는 `Method.run(ExperimentInput) -> Prediction` 인터페이스로 고정되어 있고 C는 조사 엔진 어댑터다. 실험 2~4는 정답 데이터 확보 후 구현한다(`NotImplementedError`로 표시).

### 실험 2. 행위 관계 복원 성능

**연구 질문:** 그래프 탐색이 DB에서 이벤트만 검색하는 방식보다 정확한 행위 연결을 제공하는가?

| 비교군 | 방식 |
|--------|------|
| B | 정규화 이벤트 검색 및 시간순 타임라인 |
| C | 관련 이벤트 검색 + 프로비넌스 그래프 탐색 |

**지표:** 관계별 엣지 Precision · Recall, 잘못된 연결 수, 복합 행위 질문의 정답률, 근거 추적 가능성

### 실험 3. 추론 엣지의 추가 효과

**연구 질문:** 직접 확인되지 않은 후보 관계를 탐색에 포함하면 더 많은 관계를 복원하면서도 오연결을 통제할 수 있는가?

| 비교군 | 방식 |
|--------|------|
| C1 | 명시적 참조와 직접적인 증거가 있는 엣지만 활용 |
| C2 | 위 관계에 별도 표시된 추론 후보 엣지를 추가 활용 |

추론 엣지는 근거가 부족한 상태에서 확정 엣지처럼 사용할 수 없다.  
포함 여부를 실험 조건으로 통제하고, 최종 답변에도 **후보 관계임을 표시**해야 한다.

### 실험 4. Markdown과 DB 기반 저장 방식 비교

**연구 질문:** 동일한 증거를 저장했을 때 DB 기반 검색이 Markdown 기반 검색보다 어떤 이점이 있는가?

| 비교군 | 방식 |
|--------|------|
| A | 동일한 증거를 Markdown 형태로 구성하고 검색 |
| B | 정규화 이벤트와 인덱스를 활용한 DB 검색 |

모델·질의·증거 내용·입력 예산 등은 최대한 동일하게 유지한다.  
응답 정답률과 근거 적합성뿐 아니라 사전 적재 시간, 인덱싱 비용, 질의 응답 시간, 토큰 사용량도 기록한다.

## 10. 최종 평가 지표

| 영역 | 지표 |
|------|------|
| **대상 발굴** | 엔터티 Precision · Recall · F1, Precision@5, 별칭 해소 정확도, 잘못된 병합률 |
| **관계 복원** | 엣지 Precision · Recall, 관계 유형별 오류, 다단계 행위 복원 정확도 |
| **증거 신뢰성** | 잘못된 대상 귀속률, 근거 없는 주장 비율, 미확인 상태의 적절한 보류, 반대 증거 누락률 |
| **효율성** | 적재 시간, 인덱싱 비용, 질의 시간, 토큰 사용량, 조사관 검토 시간 |

정답 대상을 더 많이 찾았더라도 **잘못된 연결이 크게 늘면** 성능이 개선된 것으로 볼 수 없다.  
추가로 발견한 후보의 정밀도와 근거 수준을 함께 평가한다.

LLM 응답 실험은 대표 질의에 대해 반복 실행하고, 평균 또는 중앙값과 결과 편차를 보고한다.  
결정론적인 추출·관계 평가를 우선 완성하고, LLM 반복 실험은 일정에 맞춰 제한된 질문으로 수행하는 것이 현실적이다.

## 11. 기존 도구와의 차별성 및 첫 주 검증

### 11.1 기존 도구

- **AgentDFIR**: 여러 AI 에이전트의 증거 수집·분석, 에이전트 주장과 도구 호출 기록, 독립적인 엔드포인트·네트워크 증거 구분, 공격 체인과 대상 주소 포함 조사 결과 제공
- **ASF Triage**: Claude Code와 Codex CLI 세션을 읽어 도구 호출·결과, 여러 세션 타임라인, 하위 에이전트 기록 조사

단순 다중 파싱, 타임라인, IOC 추출, 그래프 시각화, 증거 상태 표시만을 독창성으로 주장하지 않는다.

### 11.2 첫 주 확인 항목

| 점검 항목 | 실행 내용 |
|-----------|----------|
| 아티팩트 호환성 | 실제로 확보한 동일 테스트 자료를 기존 도구에 넣을 수 있는지 확인 |
| 대상 후보 결과 | 어떤 도메인·IP·호스트가 출력되는지, 출처가 표시되는지 확인 |
| 관계 복원 결과 | 요청·도구 호출·실행 관측·대상을 연결하는 방식 확인 |
| 비교 가능성 | 같은 입력과 같은 정답 기준으로 결과를 비교할 수 있는지 확인 |
| 기여 축 결정 | 이미 제공되는 기능과 추가로 입증할 기능을 구분 |

기존 도구를 설치해 직접 테스트하기 전에는 기능 중복을 완전히 확인했다고 말하지 않는다.

### 11.3 본 프로젝트의 기여 축

기존 네 가지 파서와 정규화 모듈을 재사용하면서,

1. **엔터티 해소**
2. **관계 기반 대상 후보 발굴**
3. **독립적인 정답을 이용한 비교 평가**

에 집중한다.

## 12. 8주 개발 일정

2개월 안에는 파서 4종을 모두 같은 깊이로 실험하기보다,  
**4종 지원은 유지**하고 **핵심 성능 평가는 2종(Cursor · Codex)**부터 수행한다.

| 주차 | 내용 |
|------|------|
| **1주** | 선행 도구 검증 및 연구 범위 확정. AgentDFIR 직접 실행 시도, 중복 기능 확인, 핵심 에이전트 선정, 평가 질문과 정답 기준 초안 작성 |
| **2주** | 정답 데이터 및 핵심 규칙 확정. 테스트 하네스·Windows 관측·Linux 서버 로그 준비, 이벤트 스키마, 상태 기준, 엣지 생성 규칙, 개발·평가 시나리오 분리 |
| **3–4주** | 대상 추출 및 관계 복원 엔진 구현. 도메인·IP·URL 정규화, 별칭 관계 처리, 명시적 엣지 및 후보 엣지 생성, 근거·모순 정보 저장 |
| **5–6주** | 조사 카드 및 후보 발굴 기능 완성. DB 검색·부분 그래프 탐색, 대상 카드, 행위 검증 카드, 원본 증거 추적, 기본 리포트 구성 |
| **7주** | 평가용 데이터에서 성능 측정. 문자열·IOC 추출, 이벤트 검색, 그래프 방식 비교. 별칭 해소·오연결·미확인 판정 성능 평가 |
| **8주** | 결과 분석 및 최종 보고. 오류 사례와 한계 분석, 비교 결과 정리, 시연 시나리오 및 발표 자료 구성 |

테스트 하네스와 정답 데이터는 1주 차부터 최소 버전을 만들어 병행한다.

## 13. 이번 범위에서 제외할 항목

- 모든 에이전트의 모든 버전별 아티팩트를 새롭게 지원하는 작업
- 계정·조직·클라우드 리소스까지 포함한 광범위한 엔터티 해소
- 실시간 위협 인텔리전스 및 외부 OSINT 통합
- 새로운 대형 그래프 알고리즘 또는 그래프 DB로의 전면 재설계
- LLM을 통한 자동 인과관계 확정
- 복잡한 UI보다 우선하지 않는 추가 시각화 기능

연구 보고서에는 다음 한계를 명시한다.

- 통제된 랩 시나리오의 한계
- 에이전트 버전 및 로그 형식 의존성
- 독립 관측 자료의 누락 가능성
- 규칙 설계자 편향
- 기존 도구와 완전히 동일한 입력을 비교하지 못할 가능성

## 14. 최종적으로 프로젝트가 제공하는 것

| 결과물 | 내용 |
|--------|------|
| **행위 복원 결과** | 어떤 요청과 도구 호출이 있었고, 어떤 명령·파일·네트워크 행위가 실제로 관측됐는지 시간순으로 확인 |
| **프로비넌스 그래프** | 행위와 대상 사이의 관계, 근거 출처, 불확실성, 모순을 확인 |
| **조사 대상 후보** | 도메인·IP·URL·호스트별 관련 행위와 발견 경로, 독립적인 관측 증거, 추가 조사 항목을 확인 |
| **정량적 평가 결과** | 문자열 추출, 이벤트 검색, 그래프 기반 관계 복원 방식을 비교해 실제로 정확도가 개선되는 부분과 개선되지 않는 부분을 제시 |

## 부록 A. 패키지 구조 (구현 기준)

```
src/
├── parsers/          # 기존 4종 파서 (유지)

├── provenance/       # 기존 실행 프로비넌스 그래프
├── investigation/    # 조사 대상 후보 발굴 (§7.4)
│   ├── models.py         # 공통 자료형·상수
│   ├── observations.py   # 독립 관측 정규화·로딩
│   ├── extraction.py     # 대상 엔터티 추출
│   ├── graph.py          # 증거 그래프
│   ├── scoring.py        # 증거 수준·점수
│   ├── cards.py          # 카드·Markdown
│   └── core.py           # 조율 + 공개 API
├── evaluation/       # 비교 실험 (§9)
│   ├── models.py         # 입력·정답·예측 계약
│   ├── methods.py        # A / B / C(엔진 어댑터)
│   ├── metrics.py        # 지표 인터페이스
│   └── experiments.py    # 실험 1a·1b (2~4는 TODO)
├── reporting/        # 기존 HTML 리포트
├── llm/              # 기존 LLM 연동
└── rewinding/        # 기존 리와인딩
```

설계서 초안에 있던 `schema/`, `entities/`, `storage/`는 아직 만들지 않았다. 엔터티 자료형은 `investigation/models.py`가 맡고, 저장소(§6)와 실험 4는 정답 데이터 확보 후 착수한다.
